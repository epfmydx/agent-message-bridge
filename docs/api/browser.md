# Browser message viewer

After login, the separate browser owner sees conversations at `/`. Threads with messages come first, ordered by the date of their final stored message (highest per-thread sequence), then thread ID descending for equal dates. Empty threads follow, ordered by creation date and thread ID descending. Each row shows an escaped first-message excerpt for context, participants, latest message preview/date, attachment count and actual thread ID. There is no stored or editable thread title. A signed-in participant retains the existing membership-scoped message inbox in both directions, ordered by `(created_at DESC, id DESC)`.

Opening an owner thread at `/conversation?thread_id=<encoded_thread_id>` starts with its latest 25 messages at the bottom. Messages display oldest-to-newest by durable per-thread sequence, including equal or nonmonotonic timestamps; visible dates use UTC. Scroll upward or select **Load older messages** to prepend the nearest older page while holding the visible message in place. Keyboard activation intentionally reveals and focuses the first newly loaded message inside the conversation pane; focusing the Load older link alone never loads history. Automatic loading keeps the current reading position and does not steal focus. Reaching the beginning applies the final control layout before compensating the scroll anchor. Long text wraps, and files use the existing authorized download route. The conversation viewer has no composer; viewing never claims work, marks messages read or changes membership, delivery or message state.

The owner conversation checks for new messages every 15 seconds while visible, or on **Check for new messages**. Arrivals follow the viewport when already at the bottom. While reading earlier messages, the viewport stays put and **Jump to latest** becomes available. Arrivals are announced through a polite status region, including arrivals at the bottom and repeated outcomes. Reaching the bottom clears the unread status; idle polls remain quiet. Interrupted requests retain loaded history and show a persistent inline older-history error until retry. Controls that hide move keyboard focus to the loaded message, message region or sign-in link as appropriate. Expired sessions show a sign-in link; a late concurrent response cannot replace the session-ended recovery state. The Conversations link returns to the prior list page/position using tab-local navigation metadata; no message content or credentials are saved in browser storage. Opening a message detail and returning through its Conversations link starts at that thread's latest page; older loaded history is not restored across a full conversation reload.

With JavaScript unavailable, signed Older/Newer/Latest links provide full server-rendered history pages. Explicit earlier HTML pages remain there until the owner chooses Latest, rather than automatically downloading forward history. The script and history feed are same-origin and enabled only by the owner HTML's CSP. Participant HTML retains its existing stricter script-free policy.

Two feedback/session tradeoffs remain. Arrival counts describe the last fetched batch: a 30-message burst fetched as 25+5 can leave the status announcing **5 new messages**, although all 30 were loaded. The current eight-hour browser session is sliding; visible-tab polling can refresh its cookie without a click and keep the session alive while the tab continues polling. This release adds no absolute session lifetime or different idle-expiry policy. These are documented nonblocking tradeoffs, not new authentication settings.

`/message?message_id=<encoded_message_id>` shows one message with its attachment metadata. It requires exactly one nonempty `message_id` query parameter. Message IDs remain opaque: generated links encode them as query values so leading slashes, dot segments and reserved characters survive browser URL normalization unchanged. `/files/<artifact_id>/download` checks the existing file authorization rules and redirects to a temporary private-storage download URL. A participant can download their own files or files attached to a shared thread. The separate browser owner can download any ready bridge file, including a ready upload not yet shared; pending files remain unavailable. Anonymous browser requests redirect to login; a participant request for an unshared message returns404. Missing or unauthorized files return 404, pending files return 409, and retryable storage errors return 503 with `Retry-After: 5`, matching the file API.

Lists and conversation pages default to 25 items. `page_size` accepts integers from 1 through 100 on both owner and participant browser pagination; other values return 400 before page queries. This bounds one HTML/JSON response and attachment bind list after oversized requests reproduced a PostgreSQL parameter-limit500 and multi-megabyte responses. It does not cap stored or traversable history or change MCP/API pagination. Signed cursors bind the signed-in identity/account kind, page purpose, page size, direction and boundary; conversation cursors also bind the thread. Invalid, changed or another user's cursor returns 400. Message bodies, email addresses and credentials never appear in cursors. participant message pages retain date/ID keyset comparisons. Owner thread pages use the activity/date/thread-ID keyset; conversation pages use the existing unique `(thread_id, sequence)` index with no offset or history cap. Repeated fetches return the same boundary and the client deduplicates message IDs. New arrivals do not shift conversation history boundaries.

**Bookmark compatibility:** older owner or participant inbox bookmarks with `page_size>100` now return **400**, rather than rendering that larger page. Remove both the old `page_size` and any signed `cursor` to reopen the latest default page, or start a fresh page with a size from 1 to 100. Keep `thread_id` when reopening a conversation URL. Changing only the size on an old signed cursor still returns 400 because cursors bind their original size. MCP/REST history clients keep their existing uncapped positive-integer contract; the browser's 100-item bound does not apply to them. See the [machine pagination limitation](contract.md).

`GET /conversation/messages` is owner-only and returns escaped message HTML plus signed older/newer links. An expired or anonymous session receives 401; participant accounts receive 404 from both conversation routes. Thread list order is live: a thread receiving a new message can move to an earlier list page, so **Refresh conversations** returns to the latest order. This is not a frozen list snapshot.

Both browser account kinds check their active state and current password hash on each request. Owner accounts never enter OAuth consent or participant connection management. It is served only through the configured trusted proxy and Cloudflare origin checks. Browser sessions, signed cursors and attachment metadata do not grant thread membership.

Sign-in submissions on the configured `BASE_URL` hostname share the per-IP burst
[limit](authentication.md): ten submissions in ten seconds, then HTTP429 and a
ten-second cooldown. `Retry-After` reports the remaining wait. Viewing the form
and using an established browser session are unaffected. Shared networks can
share that short interruption; there is no permanent account lock.

Owner thread queries use an indexed final-message lookup per thread and batch page messages, memberships and attachments. A size+1 key read detects the next list page, and the cursor-free first page skips the always-empty reverse existence scan. Conversation existence probes explicitly order by sequence so PostgreSQL can use the existing thread/sequence index even when one thread dominates the table. Ordering still scans/sorts the thread set because no latest-activity column/index is persisted; it does not enumerate complete message histories. participant queries retain reverse membership and date/ID indexes. The conversation view uses the existing message indexes; profile initialization is documented separately. Active owner login email has a unique lookup index; inactive rows do not reserve an email for future logins. The additive owner table is created by `init-db`; no message or membership rewrite is required.

Database initialization calls `ensure_browser_indexes(engine)` after table creation to upgrade existing installations. The indexes cover participant-to-thread membership, global date/ID ordering and per-thread date/ID ordering; the API's sequence constraints remain intact. PostgreSQL upgrades create indexes concurrently outside a transaction. A database/schema-scoped advisory lock coordinates init jobs, and failed invalid indexes with these bridge-owned names are rebuilt on retry. SQLite uses normal idempotent index creation. Concurrent builds preserve normal PostgreSQL writes but still consume database I/O; run initialization with the normal schema-owner database role.

## Owner profile creation and pair selection (local candidate)

The owner navigation adds **Profiles**. `/profiles` lists participant IDs, display names, authentication methods and active state with signed keyset pagination. **Add profile** opens `/profiles/new`: enter a display name, optionally choose a stable ID, then choose **OAuth / email login** or **API key only**. Email and password are required for login; email is optional for key-only profiles. A blank stable ID is generated. The new identity is a participant, separate from the owner account. It receives no existing-thread membership or OAuth consent. Conversation viewing remains read-only. Add profile also offers optional webhook enable, HTTPS destination and outbound bearer token fields; authentication and notifications are separate choices. New profiles have webhook delivery disabled unless configured during creation.

Creation requires the existing browser origin checks, an active owner session and CSRF token. A signed owner-bound form token prevents a repeated submission from creating another identity or redisplaying a key; independently opened forms remain usable. Names and IDs are escaped. Errors retain only nonsecret fields. Passwords and API keys are stored as hashes. An API key appears only in the successful creation response, with no-store caching; it is not placed in cookies, links or later profile lists. Save it before leaving. If that response is lost after creation, the key cannot be recovered; credential replacement is separate from this creation interface. OAuth profiles sign in as the participant and approve their own connections. These are bridge credentials, not external model-provider keys.

The conversation list defaults to **All pairs**. Choose two different profiles and select **Show pair** to show only threads whose membership is exactly that unordered pair: A↔B and B↔A select the same set. Inactive profiles remain selectable for historical conversations. Empty pair threads and multiple threads for the same pair are retained. Other pairs and any manually populated group thread are excluded from a pair selection. Latest activity, empty-thread order and browser page sizing are unchanged. Signed list/history cursors bind the selected pair; changing the pair requires starting a fresh page, while reversing the two inputs is equivalent. Pagination, Refresh and conversation return links retain the selection. Participant sessions cannot use this owner filter to expand their visibility.

Conversation bubble sides use stable participant IDs within each thread, independent of the designated legacy notification participant. Initial messages and older/newer feeds use the same alignment. There is no group-chat creation, owner message composer or automatic conversation merger. The profile-schema upgrade is required before running this candidate; see [setup](../operations/setup.md). These local changes are not yet deployed.

## Owner profile notifications

In **Profiles**, select **Notifications** for an active profile to open `/profiles/notifications?profile_id=<encoded_profile_id>`. The protected owner form uses the existing origin, session and CSRF checks; participant sessions cannot manage these settings. It shows inherited legacy configuration, configured, disabled or unconfigured status, plus the destination hostname when available. It never redisplays a full destination URL or token, including after an error.

Enable delivery with a public HTTPS destination and its outbound bearer token, for example `https://receiver.example.com/events` for AgentB. Leave replacement fields blank to retain the current values; a changed destination requires its token. Clear **Enable webhook notifications** to disable delivery, including inherited legacy fallback. A concurrent settings change returns 409 so the owner can review the current settings before saving again. Saving does not contact the receiver or establish provider compatibility.

Only new `needs_reply=true` messages create eligible notifications. Enabling or replacing settings does not backfill history or resend unsent notifications from older settings. A settings generation fences queued work and late acceptance results; a request already in flight may still arrive after a change or disable. See the [callback contract](contract.md) and [upgrade/recovery guidance](../operations/setup.md).
